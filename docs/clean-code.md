# راهنمای کد تمیز (Clean Code)

**درس برنامه‌نویسی پیشرفته — نسخه ۱.۰**

کد را یک بار می‌نویسید، اما ده‌ها بار می‌خوانید: خودتان، هم‌تیمی‌تان، TA و استاد. کدی که فقط «کار می‌کند» کافی نیست؛ کد باید **خوانا، قابل‌فهم و قابل‌توسعه** باشد. این راهنما قواعد مشترک ما برای هر دو پروژه (شبیه‌ساز Git و شبیه‌ساز Linux) است.

> این قواعد بخشی از معیار «کیفیت کد» در نمره‌دهی هستند. هر قاعده‌ای که رعایت نمی‌کنید، باید دلیل مشخصی برای آن داشته باشید.

---

## ۱. اصل کلی

۱. کد باید مثل متن خوانده شود، نه مثل معما.
۲. هر تابع یک کار انجام بدهد و هر کلاس یک مسئولیت داشته باشد.
۳. اگر برای فهمیدن یک خط کد نیاز به کامنت دارید، اول سعی کنید خود کد را واضح‌تر کنید.
۴. هر کدی که تحویل می‌دهید، باید بتوانید خط‌به‌خط توضیح دهید.

---

## ۲. نام‌گذاری

نام‌ها مهم‌ترین ابزار خوانایی هستند. زبان نام‌ها **انگلیسی** است و نام باید «چه بودن» یا «چه کردن» را بگوید.

### قرارداد ظاهری نام‌ها

| مورد | قالب | مثال |
| --- | --- | --- |
| کلاس و struct و enum | `PascalCase` | `Repository`, `CommitObject` |
| تابع و متد | `camelCase` | `createBranch()`, `parseCommand()` |
| متغیر محلی و پارامتر | `camelCase` | `branchName`, `fileCount` |
| متغیر عضو کلاس | پیشوند `m_` | `m_currentBranch` |
| ثابت‌ها | پیشوند `k` + `PascalCase` | `kMaxPathLength` |
| فایل‌ها | هم‌نام کلاس | `Repository.h`, `Repository.cpp` |

> این قرارداد با سبک Qt هم هماهنگ است تا در فاز ۴ کدها یکدست بمانند.

### قواعد نام‌گذاری

- **نام معنادار:** نام باید هدف را بگوید، نه نوع را.
- **بدون اختصار مبهم:** `cnt`, `tmp`, `d`, `x1` ممنوع (به‌جز شمارنده حلقه‌ی کوتاه مثل `i`).
- **تابع = فعل، کلاس = اسم:** `deleteFile()` و `FileSystem`.
- **متغیر بولی = پرسش:** `isEmpty`, `hasChanges`, `canMerge`.
- **نام‌های فارسی‌نویسی‌شده (فینگلیش) ممنوع:** `tedadFile` نه، `fileCount` بله.

```cpp
// بد
int d;                                   // تعداد روزهای گذشته
void proc(std::vector<std::string> v, int f);

// خوب
int elapsedDays;
void processCommands(const std::vector<std::string>& commands, bool verbose);
```

## ۳. توابع

- **کوتاه باشند:** هدف عملی، حداکثر حدود ۳۰ خط. اگر بلندتر شد، احتمالاً چند کار انجام می‌دهد.
- **یک کار:** اگر در توضیح تابع مجبور شدید بگویید «و ... و ...»، آن را بشکنید.
- **پارامتر کم:** حداکثر ۳ تا ۴ پارامتر. بیشتر از آن را در یک struct جمع کنید.
- **Early return:** به‌جای تودرتوی زیاد `if`، حالت‌های خطا را زود برگردانید.
- **عوارض جانبی پنهان نداشته باشند:** اسم تابع باید هرچه می‌کند را بگوید.

```cpp
// بد: تودرتو و کار زیاد در یک جا
bool commitFiles(Repository& repo, const std::string& msg) {
    if (repo.hasChanges()) {
        if (!msg.empty()) {
            // ... ۴۰ خط منطق ...
            return true;
        } else {
            return false;
        }
    } else {
        return false;
    }
}

// خوب: early return و شکستن به توابع کوچک
bool commitFiles(Repository& repo, const std::string& message) {
    if (!repo.hasChanges()) return false;
    if (message.empty())    return false;

    CommitObject commit = buildCommit(repo, message);
    repo.addCommit(commit);
    return true;
}
```

## ۴. اعداد و رشته‌های جادویی

عدد یا رشته‌ی بدون توضیح در دل کد نگذارید؛ آن را نام‌گذاری کنید.

```cpp
// بد
if (args.size() > 3) { ... }
if (command == "cm") { ... }

// خوب
constexpr std::size_t kMaxArguments = 3;
if (args.size() > kMaxArguments) { ... }
```

## ۵. کامنت‌ها

- کامنت باید **«چرا»** را بگوید، نه «چی». کد خودش «چی» را می‌گوید.
- کد کامنت‌شده (مرده) را در Repository نگذارید؛ Git تاریخچه را نگه می‌دارد.
- برای توابع و کلاس‌های عمومی، یک توضیح کوتاه درباره‌ی ورودی، خروجی و رفتار کافی است.

```cpp
// بد
i++;  // یکی به i اضافه کن

// خوب
// Git فایل‌های خالی را ردیابی نمی‌کند، پس آن‌ها را رد می‌کنیم.
if (file.isEmpty()) continue;
```

## ۶. نکات اختصاصی C++

### مدیریت حافظه (RAII)
- از `new` و `delete` مستقیم استفاده نکنید. از `std::unique_ptr` و `std::make_unique` استفاده کنید.
- `std::shared_ptr` فقط وقتی مالکیت واقعاً مشترک است.
- هر منبعی (فایل، حافظه) باید خودکار آزاد شود، نه با یادآوری دستی.

```cpp
// بد
Node* node = new Node();
// ...
delete node;   // اگر وسط کار exception بیاید، نشت حافظه

// خوب
auto node = std::make_unique<Node>();
```

### const و ارجاع
- ورودی‌های بزرگ (رشته، vector) را با `const &` بگیرید، نه کپی.
- هر چیزی که تغییر نمی‌کند `const` باشد، متدهای فقط‌خواندنی هم `const` باشند.

### سایر موارد
- `enum class` به‌جای `enum` ساده.
- `override` را برای متدهای بازنویسی‌شده بنویسید.
- حلقه‌ی range-based (`for (const auto& item : items)`) را ترجیح دهید.
- `using namespace std;` را هرگز در فایل header ننویسید.
- در header از `#pragma once` استفاده کنید.
- از کلاس‌های کتابخانه‌ی استاندارد (`std::vector`, `std::map`, `std::string`) استفاده کنید، نه آرایه‌ی خام.

---

## ۷. مدیریت خطا

- ورودی کاربر را همیشه اعتبارسنجی کنید (دستور نامعتبر، فایل ناموجود، آرگومان کم).
- یک روش یکسان در کل پروژه انتخاب کنید (مثلاً exception یا کد خطا) و ترکیب بی‌نظم نکنید.
- پیام خطا باید کاربر را راهنمایی کند، نه فقط بگوید «خطا».

```cpp
// بد
std::cout << "error\n";

// خوب
std::cerr << "Branch '" << name << "' does not exist. Use 'branch list' to see available branches.\n";
```

## ۸. ساختار پروژه و جداسازی منطق از رابط

فاز ۴ شامل رابط گرافیکی Qt است. اگر منطق برنامه از همان فاز اول به ورودی/خروجی کنسول گره بخورد، در فاز ۴ باید همه چیز را بازنویسی کنید. پس:

- **منطق اصلی** (core) نباید `std::cout` یا کلاس‌های Qt را مستقیم استفاده کند. نتیجه را برگرداند و نمایش را به لایه‌ی بالاتر بسپارد.
- **رابط** (کنسول یا Qt) فقط ورودی را بگیرد، منطق را صدا بزند و خروجی را نشان دهد.

ساختار پیشنهادی:

```
project/
├── core/        # منطق برنامه؛ بدون وابستگی به Qt و بدون چاپ مستقیم
├── cli/         # رابط خط فرمان (فازهای اول تا سوم)
├── ui/          # رابط گرافیکی Qt (فاز ۴)
├── tests/       # تست‌ها
├── README.md
└── .gitignore
```

## ۹. قالب‌بندی

- تورفتگی: ۴ فاصله (نه Tab).
- طول هر خط: حداکثر حدود ۱۰۰ کاراکتر.
- هر دستور در یک خط.
- سبک آکولاد را در کل پروژه یکسان نگه دارید.
- دو عضو گروه باید **قالب یکسانی** داشته باشند. برای این کار از `clang-format` با یک فایل `.clang-format` مشترک استفاده کنید.
- خط‌های خالی را برای جداکردن بخش‌های منطقی کد به‌کار ببرید، نه بی‌حساب.

## ۱۰. تکرار نکنید (DRY)

اگر یک تکه کد را کپی‌پیست کردید، یعنی باید یک تابع از آن بسازید. تکرار یعنی هر باگ را چند جا باید درست کنید.

## ۱۱. چک‌لیست قبل از Commit و تحویل

- [ ] پروژه بدون خطا و بدون warning کامپایل می‌شود.
- [ ] نام‌ها معنادار و طبق قرارداد هستند.
- [ ] هیچ تابعی بیش از حد بلند یا چندکاره نیست.
- [ ] عدد و رشته‌ی جادویی در کد نمانده است.
- [ ] کد کامنت‌شده و `printf` یا `cout` موقت دیباگ حذف شده‌اند.
- [ ] نشت حافظه ندارد و `new`/`delete` خام استفاده نشده است.
- [ ] منطق از رابط کاربری جدا است.
- [ ] فایل‌های کامپایل‌شده و موقت وارد Repository نشده‌اند.
- [ ] `README.md` به‌روز است.
- [ ] می‌توانم هر خط این کد را توضیح بدهم.

## ۱۲. یادآوری درباره‌ی هوش مصنوعی

استفاده از ابزارهای هوش مصنوعی برای یادگیری و رفع اشکال مجاز است، اما هر کدی که تحویل می‌دهید باید توسط خود شما **قابل‌توضیح** باشد. کدی که نتوانید در دفاع شفاهی توضیح بدهید، حتی اگر درست کار کند، امتیاز کامل نمی‌گیرد.
